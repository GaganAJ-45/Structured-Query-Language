# 1. Views

> *Everything so far has been about writing queries and running them once. A view flips that: write the query **once**, save it under a name, and from then on treat it like a table. It's the "save as" button SQL never obviously told you about.*

---

## 1. What is a View?

A **view** is a **saved `SELECT` query** stored in the database under its own name. It doesn't store data itself — every time you query a view, MySQL re-runs the underlying `SELECT` behind the scenes and hands you the result, fresh, as if it were a real table.

```sql
CREATE VIEW high_earners AS
SELECT first_name, last_name, salary, dept_id
FROM employee
WHERE salary > 100000;
```

Now you can query it exactly like a table:

```sql
SELECT * FROM high_earners ORDER BY salary DESC;
```

No `JOIN`, no `WHERE salary > 100000` repeated everywhere, no copy-pasting the same 5-line query into every script you write this month. Write the logic once, name it, reuse it forever.

> 🪟 Think of a view as a **window**, not a **box**. A box holds its own stuff — a view holds nothing; it's just a pane of glass you look through at the real `employee` table underneath. Change the data in `employee`, and the view's result changes instantly too, because it's never storing anything of its own.

---

## 2. Why Views Exist

| Problem | How a view helps |
|---|---|
| The same complex `JOIN` keeps getting rewritten in five different reports | Write it once as a view, query the view everywhere instead |
| Some users shouldn't see every column (e.g. `salary`) | Create a view that excludes sensitive columns, grant access to the view instead of the table |
| A query is correct but ugly/intimidating for a junior teammate | Hide the complexity behind a simple, well-named view |
| You want a "live" simplified version of a 3-table join without duplicating data | A view always reflects current data — no sync, no staleness |

## 3. Creating a View

### 3.1 Basic syntax

```sql
CREATE VIEW view_name AS
SELECT ... 
FROM ...
WHERE ...;
```

### 3.2 A view over a JOIN

This is where views earn their keep — wrapping up a join you don't want to retype:

```sql
CREATE VIEW employee_department_view AS
SELECT 
    e.emp_id,
    e.first_name,
    e.last_name,
    e.designation,
    e.salary,
    d.dept_name,
    d.location
FROM employee e
JOIN department d ON e.dept_id = d.dept_id;
```

```sql
-- Now this ...
SELECT first_name, dept_name FROM employee_department_view WHERE location = 'Bengaluru';

-- ... beats re-writing this every time:
SELECT e.first_name, d.dept_name 
FROM employee e JOIN department d ON e.dept_id = d.dept_id 
WHERE d.location = 'Bengaluru';
```

### 3.3 A view with aggregation

Views aren't limited to simple row filtering — a `GROUP BY` works fine inside one too:

```sql
CREATE VIEW department_salary_summary AS
SELECT 
    d.dept_name,
    COUNT(e.emp_id) AS headcount,
    ROUND(AVG(e.salary), 2) AS avg_salary,
    MAX(e.salary) AS top_salary
FROM department d
LEFT JOIN employee e ON d.dept_id = e.dept_id
GROUP BY d.dept_name;
```

```sql
SELECT * FROM department_salary_summary ORDER BY avg_salary DESC LIMIT 5;
```

That's a 3-clause query (`JOIN` + `GROUP BY` + aggregates) now callable in one word: `department_salary_summary`.

## 4. Querying a View Further

A view isn't a dead end — you can `WHERE`, `ORDER BY`, even `JOIN` on top of it, same as any table:

```sql
SELECT * 
FROM employee_department_view 
WHERE dept_name = 'Engineering' 
ORDER BY salary DESC;
```

```sql
SELECT hv.first_name, hv.salary, p.project_name
FROM high_earners hv
JOIN project p ON hv.emp_id = p.emp_id;
```

> Wait — `high_earners` doesn't have an `emp_id` column in the example above (Section 1 only selected `first_name`, `last_name`, `salary`, `dept_id`). That's a genuine gotcha worth internalizing early: **a view only exposes the columns you explicitly selected when creating it.** If you'll need a column later for joining, include it up front — go back and `CREATE OR REPLACE VIEW` (Section 6) if you forgot one.

## 5. Updating Data Through a View

Here's a genuinely surprising fact: some views are **updatable** — you can `INSERT`, `UPDATE`, or `DELETE` through them, and MySQL quietly applies the change to the real underlying table.

```sql
UPDATE high_earners
SET salary = salary * 1.10
WHERE first_name = 'Neha';
```

This actually updates the `employee` table — `high_earners` has no data of its own to update.

### 5.1 When a view is NOT updatable

A view stops being updatable the moment MySQL can't figure out which single underlying row a change should apply to. Common disqualifiers:

- The view uses `GROUP BY`, `HAVING`, aggregate functions (`COUNT`, `SUM`, `AVG`...)
- The view uses `DISTINCT`
- The view is built from a `JOIN` of 2+ tables (technically updatable in MySQL under narrow conditions, but risky and easy to get wrong — treat multi-table views as read-only in practice)
- The view uses `UNION` or `UNION ALL`
- The view's `SELECT` list includes a subquery

> `department_salary_summary` from Section 3.3, for example, is **not updatable** — it's a `GROUP BY` aggregate view. Attempting `UPDATE department_salary_summary SET avg_salary = 0` fails outright, because there's no single row in any real table that "avg_salary" corresponds to.

### 5.2 `WITH CHECK OPTION` — guarding against invisible inserts

```sql
CREATE VIEW high_earners AS
SELECT emp_id, first_name, last_name, salary, dept_id
FROM employee
WHERE salary > 100000
WITH CHECK OPTION;
```

Without `WITH CHECK OPTION`, you could technically `INSERT` a row through `high_earners` with a salary of `50000` — it would succeed, land in the real `employee` table, and then immediately vanish from the view (since it no longer matches `salary > 100000`), which is a confusing experience for whoever did the insert. `WITH CHECK OPTION` blocks any insert/update that wouldn't actually show up in the view afterward.

## 6. Modifying and Removing Views

### 6.1 `CREATE OR REPLACE VIEW` — redefining a view

```sql
CREATE OR REPLACE VIEW high_earners AS
SELECT emp_id, first_name, last_name, salary, dept_id, designation
FROM employee
WHERE salary > 100000;
```

This swaps out the view's definition in place — no need to `DROP` it first, and any permissions already granted on it stay intact.

### 6.2 `DROP VIEW` — deleting a view

```sql
DROP VIEW high_earners;
DROP VIEW IF EXISTS high_earners;   -- won't error if it's already gone
```

> Dropping a view never touches the underlying table's data — you're only deleting the saved query, not any rows. `employee` is completely unaffected by `DROP VIEW high_earners`.

### 6.3 Listing views that exist

```sql
SHOW FULL TABLES WHERE table_type = 'VIEW';
```

MySQL stores views alongside tables in `SHOW TABLES`, so this filter is how you separate "real" tables from views.

## 7. Views vs. Tables — Quick Comparison

| | Table | View |
|---|---|---|
| Stores actual data | ✅ Yes | ❌ No — just a saved query |
| Always reflects current data | Only if you keep it updated manually | ✅ Automatically, every time it's queried |
| Takes disk space for data | ✅ Yes | ❌ Practically none |
| Can be indexed directly | ✅ Yes | ❌ No (indexes live on the underlying tables) |
| Query performance | Fast — reads stored rows directly | Re-runs the underlying query every time — can be slower on heavy views |
| Can restrict column/row access | Not natively | ✅ One of its best uses |

> ⚠️ **MySQL doesn't have "materialized views"** (a view whose results *are* physically stored and refreshed on a schedule, common in PostgreSQL/Oracle). A MySQL view always re-executes live. For a view wrapping an expensive aggregate query that's hit constantly, people sometimes fake a materialized view by periodically running the query into a real summary table instead — good to know the term exists even if MySQL doesn't offer it directly.

## 8. A Realistic Combined Example

```sql
CREATE OR REPLACE VIEW active_project_leads AS
SELECT 
    e.emp_id,
    CONCAT(e.first_name, ' ', e.last_name) AS employee_name,
    d.dept_name,
    p.project_name,
    p.status
FROM employee e
JOIN department d ON e.dept_id = d.dept_id
JOIN project p ON e.emp_id = p.emp_id
WHERE p.status IN ('In Progress', 'Planned');
```

```sql
SELECT * FROM active_project_leads WHERE dept_name = 'Data Science';
```

One view, built from a 3-table join plus a `WHERE` filter, now queryable in a single line — and every one of the earlier files' concepts (`JOIN`, `WHERE`, `CONCAT`, `IN`) is doing real work inside it.

---

## Recap

- A **view** is a saved `SELECT` query with a name — it stores no data of its own, only the query definition.
- Query a view exactly like a table: `SELECT`, `WHERE`, `ORDER BY`, even further `JOIN`s all work on top of it.
- Views are great for: hiding query complexity, restricting which columns/rows someone can see, and keeping a "live" simplified version of a multi-table join.
- Not every view is **updatable** — aggregates, `DISTINCT`, `UNION`, and multi-table joins generally block `INSERT`/`UPDATE`/`DELETE` through the view.
- `WITH CHECK OPTION` stops inserts/updates that would immediately fall outside the view's own `WHERE` condition.
- `CREATE OR REPLACE VIEW` redefines a view in place; `DROP VIEW` deletes the saved query only — never the underlying data.
- MySQL views are always "live" — there's no built-in materialized view that caches results.

# 6. Subqueries

> Part of the **DQL** series. Runs against the `department` and `employee` tables — see [0.dataset.md](0.dataset.md) if you haven't set those up yet.

---

## 0. A Quick Word Before We Start

A subquery is just **a query living inside another query** — like a Russian nesting doll, except instead of dolls it's `SELECT` statements, and instead of getting smaller they get *more specific*. The inner query runs first, hands its result to the outer query, and the outer query uses that result to do its actual job.

You already met one cousin of this idea in [5.Joins.md](5.Joins.md). Subqueries solve a similar problem — pulling in info from elsewhere — but through nesting instead of side-by-side merging.

---

## 1. The Absolute Basics — A Subquery in WHERE

```sql
SELECT first_name, salary
FROM employee
WHERE salary > (
    SELECT AVG(salary) FROM employee
);
```

**How MySQL actually runs this:**
1. **Inner query runs first**, completely on its own: `SELECT AVG(salary) FROM employee` → returns one single number, say `81692.71`.
2. That number gets **substituted** into the outer query, as if you'd typed it yourself:
   ```sql
   SELECT first_name, salary FROM employee WHERE salary > 81692.71;
   ```
3. **Outer query then runs** normally against that plain number.

> Read the whole thing as one sentence: *"Show me employees who earn more than the company average."* Notice you couldn't write this in a single flat `WHERE salary > AVG(salary)` — aggregate functions like `AVG()` aren't allowed directly in `WHERE` (you learned why in [4.Group By & Having.md](4.Group%20By%20%26%20Having.md)). A subquery is exactly how you sneak an aggregate value into a row-level filter.

---

## 2. Types of Subqueries, by What They Return

Subqueries come in three "shapes," and the shape determines which operators you're allowed to use with them.

| Shape | Returns | Usable with |
|---|---|---|
| **Scalar** | A single value (1 row, 1 column) | `=`, `>`, `<`, `>=`, `<=`, `!=` |
| **Row/Column** | Multiple values (multiple rows, 1 column) | `IN`, `NOT IN`, `ANY`, `ALL` |
| **Table** | Multiple rows *and* multiple columns | Used in place of a table, after `FROM` |

Getting this wrong is the single most common subquery mistake — using `=` when the subquery can return more than one row, for example — so we'll hit each type with an example.

---

## 3. Scalar Subquery — Exactly One Value

Already saw one above. Another example:

```sql
-- Find the employee with the lowest salary
SELECT first_name, salary
FROM employee
WHERE salary = (
    SELECT MIN(salary) FROM employee
);
```

> `MIN(salary)` always returns exactly one number, so `=` is perfectly safe here. If the inner query could somehow return more than one row, `=` would throw an error — MySQL genuinely doesn't know which of the multiple values you meant to compare against.

---

## 4. Subquery with IN — Matching Against a List

When the inner query returns **multiple rows**, `=` won't work — you need `IN` instead.

```sql
-- Find all employees who work in a department located in Bengaluru
SELECT first_name, dept_id
FROM employee
WHERE dept_id IN (
    SELECT dept_id FROM department WHERE location = 'Bengaluru'
);
```

**Step by step:**
1. Inner query runs: `SELECT dept_id FROM department WHERE location = 'Bengaluru'` → returns a **list** of department IDs, say `(1, 6, 14, 22)`.
2. Outer query becomes: `WHERE dept_id IN (1, 6, 14, 22)`.
3. Every employee whose `dept_id` matches **any** value in that list gets returned.

> This exact query could also be written as a `JOIN` (see Section 8 below) — this is one of those cases where both tools solve the same problem, just differently.

### NOT IN — the flip side
```sql
-- Employees NOT in a Bengaluru-based department
SELECT first_name FROM employee
WHERE dept_id NOT IN (
    SELECT dept_id FROM department WHERE location = 'Bengaluru'
);
```

> ⚠️ **Watch out for `NULL`s with `NOT IN`.** If even one value in the inner query's result is `NULL`, `NOT IN` can unexpectedly return **zero rows** for the entire query — a classic, sneaky SQL trap. Safer alternative when `NULL`s might be involved:
```sql
WHERE dept_id NOT IN (
    SELECT dept_id FROM department WHERE location = 'Bengaluru' AND dept_id IS NOT NULL
);
```

---

## 5. Subquery in FROM — Treating a Query Like a Table

You can put an entire `SELECT` inside the `FROM` clause, and query *its result* like it's a regular table. This is often called a **derived table**.

```sql
SELECT dept_id, avg_salary
FROM (
    SELECT dept_id, AVG(salary) AS avg_salary
    FROM employee
    WHERE salary IS NOT NULL
    GROUP BY dept_id
) AS dept_averages
WHERE avg_salary > 60000;
```

**What's happening:**
1. The inner query runs first, building a **temporary result table** — one row per department, with its average salary.
2. That temporary table is given a name: `dept_averages` (a derived table **must** be aliased, or MySQL refuses to run it).
3. The outer query then treats `dept_averages` exactly like any real table, filtering on `avg_salary` directly with plain `WHERE` — no `HAVING` needed here, because by the time the outer query runs, `avg_salary` is just an ordinary column, not a live aggregate anymore.

> 😄 This is the SQL equivalent of doing your rough calculations on scratch paper first, then working off the *clean* scratch-paper numbers instead of the original messy pile — except the "scratch paper" evaporates the moment the query finishes.

---

## 6. Correlated Subqueries — The Inner Query Depends on the Outer Row

Every subquery so far has run **once**, completely independently. A **correlated subquery** is different — it re-runs **once for every row** the outer query looks at, because it references a column from the outer query.

```sql
-- Find employees earning more than their OWN department's average
SELECT e1.first_name, e1.salary, e1.dept_id
FROM employee e1
WHERE e1.salary > (
    SELECT AVG(e2.salary)
    FROM employee e2
    WHERE e2.dept_id = e1.dept_id
);
```

**Why this is different:** notice `e2.dept_id = e1.dept_id` — the inner query reaches *outside itself* to grab `e1.dept_id` from whichever outer row is currently being checked. So for every single employee, MySQL re-runs the inner query fresh, calculating *that employee's specific department's* average — not the whole company's average like Section 1's example.

> ⚠️ Correlated subqueries can get **slow** on large tables, since the inner query genuinely re-executes per outer row (100 employees here = up to 100 inner query runs). For a table with millions of rows, a `JOIN` + `GROUP BY` combo usually performs much better for the same question. Correlated subqueries are worth knowing conceptually and do show up in interviews, but treat them as a "when nothing else fits cleanly" tool, not a default choice.

---

## 7. EXISTS — Checking If a Subquery Returns Anything At All

`EXISTS` doesn't care *what* the inner query returns — only *whether it returns anything at all*. It's often faster than `IN` for large datasets, because MySQL can stop searching the moment it finds one match, instead of building the entire list first.

```sql
-- Departments that have at least one employee
SELECT dept_name
FROM department d
WHERE EXISTS (
    SELECT 1 FROM employee e WHERE e.dept_id = d.dept_id
);
```

> `SELECT 1` here is a convention — since `EXISTS` only checks for *presence*, it doesn't matter what column you select inside; people write `1` as a cheap placeholder to signal "we don't actually care about this value."

### NOT EXISTS
```sql
-- Departments with ZERO employees (an empty department)
SELECT dept_name
FROM department d
WHERE NOT EXISTS (
    SELECT 1 FROM employee e WHERE e.dept_id = d.dept_id
);
```
> This is the safer cousin of the `NOT IN` trap from Section 4 — `NOT EXISTS` doesn't break when `NULL`s are involved, unlike `NOT IN`.

---

## 8. Subquery vs JOIN — When to Use Which

Since Section 4's example could be written either way, here's the same question solved both ways side by side:

```sql
-- Using a subquery
SELECT first_name FROM employee
WHERE dept_id IN (SELECT dept_id FROM department WHERE location = 'Bengaluru');

-- Using a JOIN
SELECT e.first_name FROM employee e
JOIN department d ON e.dept_id = d.dept_id
WHERE d.location = 'Bengaluru';
```

| | Subquery | JOIN |
|---|---|---|
| Readability | Often reads more like plain English | Better when you need columns from *both* tables in the output |
| Performance | Can be slower, especially correlated ones | Generally faster, especially on large tables |
| Best for | "Does this value exist somewhere else" type questions | "Combine and display data from multiple tables" type questions |

> **Rule of thumb:** if you only need to *filter* based on another table (and don't need to *display* its columns), a subquery is often cleaner. If you need to *show* data from both tables together, reach for a `JOIN`.

---

## 9. Putting It All Together

```sql
-- Employees earning above the company average, in departments
-- that have more than 3 employees, shown with their department name
SELECT e.first_name, e.salary, d.dept_name
FROM employee e
JOIN department d ON e.dept_id = d.dept_id
WHERE e.salary > (SELECT AVG(salary) FROM employee WHERE salary IS NOT NULL)
  AND e.dept_id IN (
      SELECT dept_id FROM employee
      GROUP BY dept_id
      HAVING COUNT(*) > 3
  )
ORDER BY e.salary DESC;
```
> A `JOIN` for display, a scalar subquery for the average-salary filter, and an `IN` subquery for the department-size filter — all three techniques from this file and the last one, working together in a single realistic query.

---

## 10. Quick Recap

| Concept | What it does |
|---|---|
| Scalar subquery | Returns 1 value — usable with `=`, `>`, `<`, etc. |
| Row/column subquery | Returns multiple values — usable with `IN`, `NOT IN`, `ANY`, `ALL` |
| Subquery in `FROM` | Builds a temporary "derived table" the outer query can filter/select from |
| Correlated subquery | Re-runs once per outer row — references a column from the outer query |
| `EXISTS` / `NOT EXISTS` | Checks presence only, not the actual value — often faster than `IN`/`NOT IN` |
| Golden rule | `NOT IN` breaks silently on `NULL`s — prefer `NOT EXISTS` when unsure |

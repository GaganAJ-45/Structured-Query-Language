# 3. Aggregate Functions

> Part of the **DQL** series. Runs against the `department` and `employee` tables — see [00-dataset.md](00-dataset.md) if you haven't set those up yet.

---

## 0. A Quick Word Before We Start

Every keyword so far worked **row by row** — filter this row, sort that row. Aggregate functions are different: they take a whole *pile* of rows and squash them down into a **single number**. Think of it as SQL doing your mental math homework across 100 rows so you don't have to scroll through a spreadsheet with a calculator.

---

## 1. COUNT — How Many Rows?

```sql
-- Total number of employees
SELECT COUNT(*) FROM employee;
```
> Returns a single number: `100`.

### 1.1 COUNT(*) vs COUNT(column)

```sql
-- Counts ALL rows, including ones where salary is NULL
SELECT COUNT(*) FROM employee;

-- Counts only rows where salary is NOT NULL
SELECT COUNT(salary) FROM employee;
```
> ⚠️ **This trips people up constantly.** `COUNT(*)` counts *rows*. `COUNT(column_name)` counts *non-NULL values in that column*. Since our `employee` table has a few `NULL` salaries by design, `COUNT(*)` returns `100` while `COUNT(salary)` returns `96`. If your report ever shows a mysteriously "missing" 4 people, this is usually why.

### 1.2 COUNT with DISTINCT

```sql
-- How many different departments actually have employees?
SELECT COUNT(DISTINCT dept_id) FROM employee;
```

---

## 2. SUM — Total of a Numeric Column

```sql
-- Total salary paid out across the whole company
SELECT SUM(salary) FROM employee;
```
> `NULL` values are automatically **ignored** by `SUM` (and every aggregate function below) — they don't count as zero, they're just skipped entirely.

```sql
-- Total department budget across the company
SELECT SUM(budget) FROM department;
```

---

## 3. AVG — Average of a Numeric Column

```sql
-- Average employee salary
SELECT AVG(salary) FROM employee;
```
> Same `NULL`-skipping behavior as `SUM` — the 4 employees with no salary on file are excluded from the average, not treated as earning ₹0 (which would unfairly drag the number down).

---

## 4. MIN & MAX — Smallest and Largest Value

```sql
-- Lowest and highest salary in the company
SELECT MIN(salary), MAX(salary) FROM employee;

-- Oldest and most recently hired employee dates
SELECT MIN(hire_date), MAX(hire_date) FROM employee;
```
> `MIN`/`MAX` aren't limited to numbers — they work on dates and even text (alphabetically) too.

```sql
-- Alphabetically first and last department name
SELECT MIN(dept_name), MAX(dept_name) FROM department;
```

---

## 5. Combining Aggregates with WHERE

Aggregate functions can be combined with a `WHERE` clause — the filter happens **first**, then the aggregate runs only on what's left.

```sql
-- Average salary, but only for the Engineering department (dept_id = 1)
SELECT AVG(salary) FROM employee WHERE dept_id = 1;

-- How many employees were hired in 2023 or later?
SELECT COUNT(*) FROM employee WHERE hire_date >= '2023-01-01';
```

---

## 6. Aliasing Aggregate Results

Aggregate output columns come back with an ugly default name like `AVG(salary)` unless you alias them — always alias them.

```sql
SELECT
    COUNT(*)      AS total_employees,
    SUM(salary)   AS total_payroll,
    AVG(salary)   AS average_salary,
    MIN(salary)   AS lowest_salary,
    MAX(salary)   AS highest_salary
FROM employee;
```

**Sample output:**

| total_employees | total_payroll | average_salary | lowest_salary | highest_salary |
|---|---|---|---|---|
| 100 | 7842500.00 | 81692.71 | 25100.00 | 149800.00 |

*(your exact numbers will vary slightly depending on your random dataset run)*

> 😄 Somewhere in that table is one employee earning ₹1,49,800 a month, and somewhere else one earning ₹25,100. SQL won't tell you if that's fair — it just does the math.

## 7. Aggregates Without GROUP BY vs With GROUP BY

Everything in this file so far produces **one single row** of output — one total, one average, across the *entire* table.

```sql
-- ONE row back: the average salary of ALL 100 employees combined
SELECT AVG(salary) FROM employee;
```

But usually you don't want one giant blended average — you want it **per department**, **per designation**, etc. That's where `GROUP BY` comes in, and it deserves its own file because combining it with `HAVING` is where most learners either "get" SQL or get stuck.

```sql
-- Sneak preview of what's coming next
SELECT dept_id, AVG(salary)
FROM employee
GROUP BY dept_id;
```
> This one returns **multiple rows** — one average per department, not one average for everybody. We'll break this down properly in the next file.

---

## 8. Quick Recap

| Function | What it returns |
|---|---|
| `COUNT(*)` | Number of rows (NULLs included) |
| `COUNT(column)` | Number of non-NULL values in that column |
| `SUM(column)` | Total of all non-NULL numeric values |
| `AVG(column)` | Average of all non-NULL numeric values |
| `MIN(column)` | Smallest value (works on numbers, dates, text) |
| `MAX(column)` | Largest value (works on numbers, dates, text) |
| Golden rule | Aggregate functions **ignore `NULL`s** — they don't treat them as zero |

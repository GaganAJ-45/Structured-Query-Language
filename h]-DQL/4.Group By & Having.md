# 4. GROUP BY & HAVING

## 0. A Quick Word Before We Start

The last file gave you **one number for the whole table** — one total, one average, one count. Useful, but real questions are rarely that flat. Nobody actually asks *"what's the average salary at the company?"* — they ask *"what's the average salary **per department**?"* That "per ___" is exactly what `GROUP BY` gives you.

---

## 1. The Execution Order — Read This Before Anything Else

Beginners almost always get tripped up because SQL runs a query in a **different order** than you write it in. For a query using `WHERE` and `GROUP BY`, the real execution order is:

```
1. FROM   →   2. WHERE   →   3. GROUP BY   →   4. SELECT
```

Not top-to-bottom like you typed it. Let's walk through it with an actual query:

```sql
SELECT dept_id, AVG(salary)
FROM employee
WHERE salary IS NOT NULL
GROUP BY dept_id;
```

**Step 1 — `FROM employee`**
SQL loads the full table — all 100 employee rows.

**Step 2 — `WHERE salary IS NOT NULL`**
Filters **individual rows**, one at a time, before any grouping. The 4 employees with a missing salary get dropped here. You're left with 96 plain, ungrouped rows.

**Step 3 — `GROUP BY dept_id`**
SQL now takes those 96 leftover rows and **physically bundles them into buckets**, one bucket per unique `dept_id`:

```
Bucket dept_id=1:  [emp5, emp12, emp30, emp44, ...]
Bucket dept_id=2:  [emp2, emp9, emp51, ...]
Bucket dept_id=3:  [emp7, emp8, ...]
...
```

At this point, individual "rows" stop mattering — you now have **groups**, each holding several employees.

**Step 4 — `SELECT dept_id, AVG(salary)`**
This is where beginners usually trip: `SELECT` no longer runs per original row — it runs **once per bucket**.

For each bucket:
- `dept_id` → the label of that bucket
- `AVG(salary)` → SQL reaches into that bucket, grabs every salary inside it, and returns one average

So the 96 individual rows collapse down into **one output row per department**:

| dept_id | AVG(salary) |
|---|---|
| 1 | 68450.00 |
| 2 | 52100.00 |
| 3 | 74900.00 |

### The one-line rule to remember
> **`WHERE` filters individual rows. `GROUP BY` merges rows into buckets. `SELECT` (with an aggregate) then runs once per bucket, not once per row.**

### Why this query fails
```sql
SELECT dept_id, first_name, AVG(salary)   -- ❌ ERROR
FROM employee
GROUP BY dept_id;
```
`first_name` belongs to a **single employee**, but by the time `SELECT` runs, that single row no longer exists on its own — only a bucket of many employees does. SQL has no way to know *which* employee's name you meant, so it refuses to guess. (This is also why the golden rule below exists.)

> **Golden rule of `GROUP BY`:** every column in your `SELECT` list must be either (a) inside `GROUP BY`, or (b) wrapped in an aggregate function like `AVG()`, `COUNT()`, `SUM()`. No exceptions, no matter how "obvious" the answer feels to a human.

## 2. GROUP BY — Basic Syntax

```sql
SELECT dept_id, COUNT(*) AS employee_count
FROM employee
GROUP BY dept_id;
```
> Reads as: *"For each department, tell me how many employees are in it."*

**Sample output (first few rows):**

| dept_id | employee_count |
|---|---|
| 1 | 6 |
| 2 | 3 |
| 3 | 5 |
| 4 | 2 |

### 2.1 Grouping with multiple aggregate functions
```sql
SELECT
    dept_id,
    COUNT(*)     AS total_employees,
    AVG(salary)  AS avg_salary,
    MIN(salary)  AS lowest_salary,
    MAX(salary)  AS highest_salary
FROM employee
WHERE salary IS NOT NULL
GROUP BY dept_id;
```
> One query, and you get a full salary breakdown per department in one shot — this is basically what an HR dashboard is doing behind the scenes.

### 2.2 Grouping by multiple columns

```sql
SELECT dept_id, designation, COUNT(*) AS count
FROM employee
GROUP BY dept_id, designation;
```
> Buckets now form on the **combination** of both columns — e.g., "Department 1 + Senior Developer" is its own bucket, separate from "Department 1 + Junior Developer." Think of it as grouping by section *and* by roll-number range, instead of just section alone.

### 2.3 Joining GROUP BY with the department table (a natural next step)

```sql
SELECT d.dept_name, COUNT(e.emp_id) AS employee_count
FROM department d
JOIN employee e ON d.dept_id = e.dept_id
GROUP BY d.dept_name;
```
> This one shows department **names** instead of raw IDs — much more readable. (We haven't formally covered `JOIN` yet — that's a couple files away — but it's worth previewing here since `GROUP BY` and `JOIN` show up together constantly in real queries.)

## 3. HAVING — Filtering Groups (Not Rows)

`WHERE` filters rows **before** grouping happens. `HAVING` filters **buckets, after** they've already been formed. If you want to filter based on an aggregate result (like an average, a count, a sum), `HAVING` is the only correct tool — `WHERE` simply doesn't have access to aggregate values yet at the point it runs.

```sql
-- Only show departments with more than 4 employees
SELECT dept_id, COUNT(*) AS total_employees
FROM employee
GROUP BY dept_id
HAVING COUNT(*) > 4;
```

### 3.1 Why this fails, and HAVING is the fix

```sql
-- ❌ ERROR — COUNT(*) doesn't exist yet at the WHERE stage
SELECT dept_id, COUNT(*)
FROM employee
WHERE COUNT(*) > 4
GROUP BY dept_id;
```
> At the moment `WHERE` runs, grouping hasn't happened yet — so there's no bucket, and therefore no count to check against. `HAVING` runs *after* `GROUP BY`, once counts/averages/sums actually exist.

### 3.2 WHERE and HAVING together in the same query

They're not mutually exclusive — most real queries use both, each doing its own job:

```sql
SELECT dept_id, AVG(salary) AS avg_salary
FROM employee
WHERE salary IS NOT NULL        -- Step 1: drop rows with no salary on file
GROUP BY dept_id                -- Step 2: bucket the remaining rows by department
HAVING AVG(salary) > 50000;     -- Step 3: keep only buckets averaging above 50k
```

### 3.3 Full execution order, now with HAVING included

```
1. FROM   →   2. WHERE   →   3. GROUP BY   →   4. HAVING   →   5. SELECT
```
> `HAVING` slots in right after `GROUP BY` and right before `SELECT` — it decides which buckets survive to actually appear in your results.

---

## 4. WHERE vs HAVING — Side by Side

| | `WHERE` | `HAVING` |
|---|---|---|
| Filters | Individual rows | Groups/buckets |
| Runs | Before `GROUP BY` | After `GROUP BY` |
| Can use aggregate functions? | ❌ No (`COUNT`, `AVG`, etc. don't exist yet) | ✅ Yes |
| Works without `GROUP BY`? | ✅ Yes, always | ⚠️ Technically yes, but rare — treats the whole table as one group |
| Typical use | `WHERE salary > 40000` | `HAVING COUNT(*) > 5` |

> 😄 If `WHERE` and `HAVING` were bouncers at a club: `WHERE` checks IDs at the front door, one person at a time, before anyone's even grouped into tables. `HAVING` walks around *after* everyone's already seated in groups, and kicks out entire tables that don't meet the group's criteria (like "table must have at least 4 people ordering food").

## 5. Putting It All Together

```sql
-- Departments where the average salary (excluding missing salaries)
-- is above 60,000, showing only departments with at least 3 such employees,
-- sorted by average salary, highest first
SELECT
    dept_id,
    COUNT(*)      AS employees_counted,
    AVG(salary)   AS avg_salary
FROM employee
WHERE salary IS NOT NULL
GROUP BY dept_id
HAVING COUNT(*) >= 3 AND AVG(salary) > 60000
ORDER BY avg_salary DESC;
```

Read as one sentence: *"Look at employees with a known salary, group them by department, keep only departments with at least 3 such employees averaging more than ₹60,000, and show the richest departments first."*

---

## 6. Quick Recap

| Keyword | What it does |
|---|---|
| `GROUP BY` | Bundles rows into buckets based on matching column value(s) |
| Aggregate in `SELECT` | Runs **once per bucket**, not once per row, once `GROUP BY` is used |
| `HAVING` | Filters buckets **after** grouping — the only place aggregate conditions belong |
| `WHERE` | Filters individual rows **before** grouping — no aggregates allowed here |
| Golden rule | Every non-aggregated column in `SELECT` must appear in `GROUP BY` |
| Execution order | `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT` |

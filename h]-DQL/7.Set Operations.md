# 7. Set Operations — UNION & UNION ALL

> Part of the **DQL** series. Runs against the `department`, `employee`, and `project` tables — see [0.dataset.md](0.dataset.md) if you haven't set those up yet (including the `project` table addendum).

---

## 0. A Quick Word Before We Start

Every `JOIN` you've written so far combined tables **side by side** — more columns, same number of rows-ish. `UNION` does the opposite: it stacks two query results **on top of each other**, combining rows from two separate `SELECT`s into one single list. Think of `JOIN` as gluing two tables together left-to-right, and `UNION` as stapling two result sets together top-to-bottom.

You've actually already used `UNION` once — remember the `FULL OUTER JOIN` workaround in [5.Joins.md](5.Joins.md)? That's exactly this concept, just without the full explanation. Let's fix that now.

---

## 1. UNION — Combining Two Result Sets, Removing Duplicates

```sql
SELECT first_name FROM employee WHERE dept_id = 1
UNION
SELECT manager_name FROM department WHERE dept_id = 1;
```

**What happens:**
1. The first `SELECT` runs, returning a list of names.
2. The second `SELECT` runs, returning another list of names.
3. `UNION` **stacks both lists into one**, then automatically **removes any exact duplicate rows** between them.

> If an employee's name happens to also be that department's manager name (unlikely with your data, but possible), `UNION` would show that name **only once** — not twice.

---

## 2. The Two Non-Negotiable Rules of UNION

Unlike `JOIN`, which needs a matching column value, `UNION` has stricter structural rules:

### Rule 1 — Same number of columns in every SELECT
```sql
-- ❌ ERROR — left has 2 columns, right has 1
SELECT first_name, salary FROM employee
UNION
SELECT dept_name FROM department;
```

### Rule 2 — Columns must be compatible types, in the same order
```sql
-- ✅ Works — column 1 is text on both sides, column 2 is text on both sides
SELECT first_name, designation FROM employee
UNION
SELECT dept_name, location FROM department;
```
```sql
-- ⚠️ Technically runs, but produces a confusing mixed-type column — avoid this
SELECT first_name, salary FROM employee   -- salary is a number
UNION
SELECT dept_name, budget FROM department; -- budget is also a number, so this actually works
                                           -- but pairing first_name with dept_name in one column is nonsensical
```
> MySQL checks that types are **compatible** (numbers with numbers, text with text) — it does **not** check whether combining them makes logical sense. That part is entirely on you.

### Column names in the final result
The output column names always come from the **first** `SELECT` — the second query's column names are ignored entirely, even if they're different.

```sql
SELECT first_name AS person_name FROM employee
UNION
SELECT dept_name FROM department;
-- Final result column is named "person_name" for BOTH halves, regardless of the second query's column name
```

---

## 3. UNION ALL — Same Thing, But Keeps Duplicates

```sql
SELECT first_name FROM employee WHERE dept_id = 1
UNION ALL
SELECT manager_name FROM department WHERE dept_id = 1;
```

**The only difference from `UNION`:** duplicate rows are **not** removed. Whatever the two `SELECT`s return, exactly that many rows show up in the final result — no deduplication pass.

### Why you'd actually want duplicates kept
`UNION` has to do extra work behind the scenes to find and remove duplicates (essentially sorting the whole combined result and comparing neighbors). `UNION ALL` skips that step entirely, which makes it **faster** — sometimes significantly, on large result sets.

> **Rule of thumb:** if you already know there can't be any duplicates between your two queries (e.g., you're combining data from two mutually exclusive filters), always use `UNION ALL` instead of plain `UNION` — you get the same correct result, just quicker, since MySQL isn't wasting effort checking for duplicates that were never going to exist.

---

## 4. UNION vs UNION ALL — Side by Side

| | `UNION` | `UNION ALL` |
|---|---|---|
| Removes duplicates? | ✅ Yes | ❌ No |
| Speed | Slower (has to check for duplicates) | Faster |
| Row count guarantee | May be less than the sum of both queries | Always exactly the sum of both queries |
| Use when | You genuinely need unique combined results | You know there's no overlap, or duplicates are fine/expected |

---

## 5. A Practical Example — Building a Combined "People" List

```sql
-- One combined list: every employee's name, AND every department manager's name,
-- with a label showing which "role" each name came from
SELECT first_name AS person_name, 'Employee' AS role
FROM employee

UNION ALL

SELECT manager_name, 'Manager'
FROM department;
```

**Sample output (first few rows):**

| person_name | role |
|---|---|
| Anjali | Employee |
| Kiara | Employee |
| Rohan Sharma | Manager |
| Ananya Reddy | Manager |

> Adding a literal string like `'Employee'` as its own column is a common `UNION` trick — it tags each row with **where it came from**, since once two result sets are stacked together, there's otherwise no way to tell which original query a given row belongs to.

> 😄 Without that label column, you'd end up with one long anonymous list of names, and absolutely no way to know if "Rohan Sharma" is an employee or someone's manager — which, in a company as org-chart-obsessed as yours (25 departments, remember), is exactly the kind of confusion you'd want to avoid.

## 6. UNION with ORDER BY — One Rule to Remember

`ORDER BY` can only be used **once**, at the very end of the whole `UNION`, sorting the final combined result — not attached to each individual `SELECT`.

```sql
-- ✅ Correct — one ORDER BY, at the end, sorting the combined result
SELECT first_name AS person_name FROM employee
UNION
SELECT manager_name FROM department
ORDER BY person_name;
```

```sql
-- ❌ ERROR — ORDER BY is not allowed inside the middle of a UNION like this
SELECT first_name FROM employee ORDER BY first_name
UNION
SELECT manager_name FROM department;
```

> Also notice: the `ORDER BY` at the end uses `person_name` — the **first** query's column alias, per the naming rule from Section 2.

## 7. Revisiting the FULL OUTER JOIN Workaround (Now Fully Explained)

Back in [5.Joins.md](5.Joins.md), this appeared without much detail:

```sql
SELECT e.first_name, d.dept_name
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id

UNION

SELECT e.first_name, d.dept_name
FROM employee e
RIGHT JOIN department d ON e.dept_id = d.dept_id;
```

**Now you can actually read this properly:**
1. **First half:** `LEFT JOIN` — every employee, matched or not.
2. **Second half:** `RIGHT JOIN` — every department, matched or not.
3. **`UNION`** stacks both results together, and since any row that matched successfully would appear identically in *both* halves, `UNION`'s automatic duplicate-removal cleans that overlap up — leaving exactly one copy of every genuinely matched row, plus the unmatched employees from the left, plus the unmatched departments from the right.

> This is the one place `UNION` (not `UNION ALL`) genuinely matters for correctness — using `UNION ALL` here would **double up** every properly matched employee-department pair, since they'd legitimately appear once in each half.

---

## 8. Quick Recap

| Keyword | What it does |
|---|---|
| `UNION` | Stacks two `SELECT` results together, removes duplicate rows |
| `UNION ALL` | Same, but keeps duplicates — faster |
| Column rule | Both `SELECT`s need the same number of columns, in compatible types |
| Naming rule | Final output column names come from the **first** `SELECT` only |
| `ORDER BY` placement | Goes once, at the very end of the whole `UNION`, never mid-query |
| Golden rule | Use `UNION ALL` by default unless you specifically need duplicates removed — it's faster and just as correct when no overlap exists |

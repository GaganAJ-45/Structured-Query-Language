# 8. Execution Order Recap

> *You've now met every clause in the SQL query. This file doesn't teach anything new — it's the cheat sheet that ties them all together. Pin this one, it's the page you'll come back to the most.*

---

## 1. The Big Picture

Here's the thing that trips up almost everyone learning SQL: **the order you *write* a query is not the order it *runs*.**

You write it like this:

```sql
SELECT ...
FROM ...
WHERE ...
GROUP BY ...
HAVING ...
ORDER BY ...
LIMIT ...
```

But MySQL executes it like this:

```
1. FROM        → figure out which table(s) we're pulling from
2. JOIN        → combine tables together, row by row
3. WHERE       → throw out rows that don't match the condition
4. GROUP BY    → bundle remaining rows into buckets
5. HAVING      → throw out buckets that don't match the condition
6. SELECT      → pick/compute the columns to show
7. DISTINCT    → remove duplicate result rows (if used)
8. ORDER BY    → sort the final result
9. LIMIT/OFFSET → cut down to the requested number of rows
```

Written order and execution order are basically opposites in the middle, and that mismatch is the root of *every* "why doesn't this work" moment in SQL. Once this order is burned into memory, half of SQL's weird rules stop being weird and start being obvious.

---

## 2. The Full Flow, Visually

```
 ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌──────────┐    ┌─────────┐
 │  FROM   │ →  │  JOIN   │ →  │  WHERE  │ →  │ GROUP BY │ →  │ HAVING  │
 └─────────┘    └─────────┘    └─────────┘    └──────────┘    └─────────┘
  pick table    combine tables  filter rows    bundle rows     filter buckets
                                (row-by-row)    into buckets    (bucket-by-bucket)

      ↓
 ┌─────────┐    ┌──────────┐    ┌──────────┐    ┌────────────────┐
 │ SELECT  │ →  │ DISTINCT │ →  │ ORDER BY │ →  │ LIMIT / OFFSET  │
 └─────────┘    └──────────┘    └──────────┘    └────────────────┘
  pick/compute   dedupe rows     sort result      trim result
  columns
```

Not every query uses every stage — a simple `SELECT * FROM employee;` only touches FROM and SELECT. But whenever a clause *is* present, it always fires in this order, never the order it was typed in.

## 3. One Query, Every Stage Labeled

Let's run one realistic query through the entire pipeline so you can see each stage actually do its job.

```sql
SELECT 
    d.dept_name,
    COUNT(*) AS emp_count,
    AVG(e.salary) AS avg_salary
FROM employee e
JOIN department d ON e.dept_id = d.dept_id
WHERE e.salary IS NOT NULL
GROUP BY d.dept_name
HAVING COUNT(*) > 3
ORDER BY avg_salary DESC
LIMIT 5;
```

Here's what MySQL actually does, step by step:

| Step | Clause | What happens here |
|---|---|---|
| 1 | `FROM employee e` | Start with the `employee` table, aliased `e` |
| 2 | `JOIN department d ON ...` | Attach matching `department` rows to each employee |
| 3 | `WHERE e.salary IS NOT NULL` | Drop every employee row with a `NULL` salary — **before** any grouping happens |
| 4 | `GROUP BY d.dept_name` | Bundle the surviving rows into one bucket per department |
| 5 | `HAVING COUNT(*) > 3` | Keep only buckets (departments) with more than 3 employees in them |
| 6 | `SELECT d.dept_name, COUNT(*), AVG(e.salary)` | For each surviving bucket, compute the dept name, headcount, and average salary |
| 7 | *(no DISTINCT here)* | skipped |
| 8 | `ORDER BY avg_salary DESC` | Sort the final department list by average salary, highest first |
| 9 | `LIMIT 5` | Keep only the top 5 rows after sorting |

Notice step 3 vs step 5: `WHERE` filters individual **employees** before grouping, `HAVING` filters entire **departments** after grouping. Same keyword family, completely different stage of the pipeline — that's not a coincidence, it's the whole reason both exist.

## 4. Why This Order Explains SQL's "Weird" Rules

This is the part that makes the execution order actually *useful* instead of just trivia. A bunch of rules that feel arbitrary are really just consequences of this order.

### 4.1 Why you can't use a `SELECT` alias in `WHERE`, `GROUP BY`, or `HAVING`

```sql
-- This fails:
SELECT salary * 12 AS annual_salary
FROM employee
WHERE annual_salary > 500000;   -- ❌ Unknown column 'annual_salary'
```

Look at the execution order: `WHERE` runs in **step 3**. `SELECT` — the clause that actually creates the `annual_salary` alias — doesn't run until **step 6**. MySQL hits `WHERE` and `annual_salary` simply doesn't exist yet. You're asking it to filter using a column it hasn't invented yet.

Same story for `GROUP BY` (step 4) and `HAVING` (step 5) — both run before `SELECT`'s step 6, so neither can see a `SELECT` alias either.

### 4.2 Why you *can* use a `SELECT` alias in `ORDER BY`

```sql
-- This works fine:
SELECT salary * 12 AS annual_salary
FROM employee
ORDER BY annual_salary DESC;   -- ✅ totally legal
```

`ORDER BY` is **step 8** — it runs *after* `SELECT` (step 6). By the time `ORDER BY` fires, `annual_salary` already exists as a real, computed column. It's not a special exception for `ORDER BY`; it's just the only clause late enough in the pipeline to see what `SELECT` built.

> 🔗 First covered in **`2.Sorting & Limiting.md`**, explained in depth in **`4.Group By & Having.md`**. If you only remember one row from this whole file, make it this one — it's the single most common "wait, why does this work here but not there" moment in SQL.

### 4.3 Why `WHERE` can't use aggregate functions, but `HAVING` can

```sql
-- This fails:
SELECT dept_id, COUNT(*) 
FROM employee
WHERE COUNT(*) > 3     -- ❌ Invalid use of group function
GROUP BY dept_id;

-- This works:
SELECT dept_id, COUNT(*) 
FROM employee
GROUP BY dept_id
HAVING COUNT(*) > 3;   -- ✅
```

`WHERE` (step 3) runs **before** `GROUP BY` (step 4) — so at the point `WHERE` is evaluating rows, no buckets exist yet, which means there's nothing for `COUNT(*)` to count. `HAVING` (step 5) runs **after** grouping, so it's evaluating fully-formed buckets and `COUNT(*)` makes perfect sense there.

### 4.4 Why the non-aggregated-column rule in `GROUP BY` exists

```sql
-- This fails (or silently picks a random row, in non-strict SQL modes):
SELECT first_name, dept_id, COUNT(*)
FROM employee
GROUP BY dept_id;   -- ❌ first_name isn't grouped and isn't aggregated
```

Once `GROUP BY` (step 4) collapses many employee rows into one bucket per `dept_id`, there's no single `first_name` left to return for that bucket — there might be 20 different first names in there. `SELECT` (step 6) can only ask for columns that are either (a) in the `GROUP BY` list, or (b) wrapped in an aggregate like `COUNT()`/`AVG()` that knows how to collapse many values into one.

### 4.5 Why `LIMIT` always acts last, no matter where it's "attached" in your head

A lot of beginners assume `LIMIT 5` means "only look at 5 rows." It doesn't — it means "after everything else is done (filtering, grouping, sorting), hand me only the first 5." That's why `ORDER BY ... LIMIT 5` reliably gives you the *top* 5, not just "5 random matching rows." Sorting (step 8) always finishes before trimming (step 9) ever starts.

## 5. Quick-Reference Table

| Stage | Clause | Operates on | Can reference `SELECT` aliases? | Can use aggregates? |
|---|---|---|---|---|
| 1 | `FROM` | table(s) | — | — |
| 2 | `JOIN` | combined rows | ❌ | ❌ |
| 3 | `WHERE` | individual rows | ❌ | ❌ |
| 4 | `GROUP BY` | individual rows → buckets | ❌ | ❌ |
| 5 | `HAVING` | buckets | ❌ | ✅ |
| 6 | `SELECT` | buckets or rows | n/a (this is where they're born) | ✅ |
| 7 | `DISTINCT` | result rows | ✅ | — |
| 8 | `ORDER BY` | result rows | ✅ | ✅ |
| 9 | `LIMIT`/`OFFSET` | result rows | — | — |

---

## 6. The One-Line Mnemonic

If you forget everything else, keep this sentence:

> **"Find it, join it, filter it, bucket it, filter the buckets, show it, sort it, trim it."**

```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
 find    join   filter   bucket    filter    show     sort     trim
                 it        it      buckets    it        it       it
```

## Recap

- SQL is **written** top-to-bottom, but **executed** in a fixed, different order: `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET`.
- Almost every "why can't I do this" moment in SQL traces back to a clause trying to use something that hasn't been computed yet in the execution order.
- The big one to remember: `ORDER BY` is the only clause late enough to use a `SELECT` alias.
- `WHERE` filters rows before grouping; `HAVING` filters buckets after grouping — same job, different stage.
- `LIMIT` always runs dead last, after sorting — which is exactly why `ORDER BY ... LIMIT` reliably gives you a true "top N."

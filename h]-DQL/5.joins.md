# 5. JOINs

> Part of the **DQL** series. Runs against the `department` and `employee` tables — see [0.dataset.md](0.dataset.md) if you haven't set those up yet.

---

## 0. A Quick Word Before We Start

Every file so far has quietly ignored the fact that your database has **two tables**. We've been living entirely inside `employee`, occasionally glancing at `dept_id` like it's just some random number. Today that number finally gets to mean something.

`JOIN` is how SQL answers the question: *"I have related data sitting in two different tables — can I see it together, in one result?"* And honestly, this is where SQL stops feeling like a spreadsheet with extra steps and starts feeling like an actual relational database.

---

## 1. Why JOIN Even Exists

Try this first, without any join:

```sql
SELECT first_name, dept_id FROM employee;
```

**Output:**

| first_name | dept_id |
|---|---|
| Aditya | 1 |
| Nisha | 2 |
| Kabir | 1 |

Cool. Except `dept_id = 1` means nothing to a human reading this report. Was that "Engineering"? "Legal"? We don't know — that information lives in a completely different table, `department`. A `JOIN` is simply SQL's way of saying: *"Go look up that ID in the other table, and bring back what it actually means."* Think of `dept_id` as a locker number, and `JOIN` as the person who actually walks over and tells you what's inside locker #1.

---

## 2. INNER JOIN — "Only Show Matches on Both Sides"

The most common join by a wide margin. It returns rows **only when there's a match in both tables**.

```sql
SELECT e.first_name, e.designation, d.dept_name
FROM employee e
INNER JOIN department d ON e.dept_id = d.dept_id;
```

**What's happening:**
- `e` and `d` are **table aliases** — shortcuts so you don't have to type `employee.first_name` and `department.dept_name` every time. Think of them as nicknames, not renames.
- `ON e.dept_id = d.dept_id` is the **matching condition** — "connect a row in `employee` to a row in `department` when their `dept_id` values are equal."

**Sample output:**

| first_name | designation | dept_name |
|---|---|---|
| Aditya | Senior Developer | Engineering |
| Kabir | Manager | Engineering |
| Nisha | Analyst | Sales |

> If an employee somehow had a `dept_id` that doesn't exist in the `department` table (shouldn't happen if your foreign key is set up correctly — see [d]-DDL.md](../d%5D-DDL.md)), `INNER JOIN` would just quietly leave that employee out entirely. No error, no warning — they just don't show up. This surprises beginners constantly, so keep it in the back of your mind.

---

## 3. LEFT JOIN — "Show Everyone From the Left Table, Matched or Not"

```sql
SELECT e.first_name, e.dept_id, d.dept_name
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id;
```

**The rule:** every row from the **left** table (`employee`, since it's listed first/on the left of `LEFT JOIN`) appears in the result **no matter what** — matched or not. If there's no matching department, the department columns just show up as `NULL`.

**Sample output:**

| first_name | dept_id | dept_name |
|---|---|---|
| Aditya | 1 | Engineering |
| Ravi | 30 | NULL |

> `dept_id = 30` doesn't exist in our 25-department table, so Ravi still shows up — SQL just shrugs and fills `dept_name` with `NULL` instead of dropping him from the results. `INNER JOIN` would have made Ravi disappear entirely; `LEFT JOIN` keeps him, just flags the mismatch.

### When you'd actually use this
*"Show me every employee, and their department if they have one"* — useful for finding **orphaned data** (employees pointing to departments that don't exist, or in a real app: customers with no orders, products with no reviews). `LEFT JOIN` + `WHERE right_table_column IS NULL` is a classic pattern for finding exactly this kind of gap.

```sql
-- Find employees whose dept_id doesn't match any real department
SELECT e.first_name, e.dept_id
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id
WHERE d.dept_id IS NULL;
```

## 4. RIGHT JOIN — "Show Everyone From the Right Table, Matched or Not"

The mirror image of `LEFT JOIN`.

```sql
SELECT e.first_name, d.dept_name
FROM employee e
RIGHT JOIN department d ON e.dept_id = d.dept_id;
```

**The rule:** every row from the **right** table (`department`) appears, matched or not. If a department currently has zero employees, it still shows up, with `first_name` as `NULL`.

**Sample output:**

| first_name | dept_name |
|---|---|
| Aditya | Engineering |
| NULL | Compliance |

> Department "Compliance" apparently has nobody assigned to it yet — `RIGHT JOIN` surfaces that instead of hiding it.

> 😄 **Honest tip:** almost nobody actually writes `RIGHT JOIN` in real code. You can always rewrite a `RIGHT JOIN` as a `LEFT JOIN` by just swapping which table comes first — and most developers do exactly that, purely so every join in a codebase reads the same direction. `RIGHT JOIN` mostly exists so you *recognize* it when someone else's older code uses it.

```sql
-- This RIGHT JOIN...
SELECT e.first_name, d.dept_name
FROM employee e
RIGHT JOIN department d ON e.dept_id = d.dept_id;

-- ...is identical to this LEFT JOIN, just with tables swapped
SELECT e.first_name, d.dept_name
FROM department d
LEFT JOIN employee e ON e.dept_id = d.dept_id;
```

## 5. FULL OUTER JOIN — "Show Everything From Both Sides"

Combines `LEFT` and `RIGHT` — every row from **both** tables, matched or not.

> ⚠️ **MySQL does not support `FULL OUTER JOIN` directly.** (PostgreSQL and SQL Server do — this is one of the rare places MySQL is the odd one out.) You have to fake it using `UNION`:

```sql
SELECT e.first_name, d.dept_name
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id

UNION

SELECT e.first_name, d.dept_name
FROM employee e
RIGHT JOIN department d ON e.dept_id = d.dept_id;
```

> Read as: *"Give me everyone from the left side (matched or not), combined with everyone from the right side (matched or not), with `UNION` cleaning out any exact duplicate rows that show up in both halves."* We'll cover `UNION` itself properly in a later file — for now, just know this trick exists for when you genuinely need the full picture from both tables.

## 6. SELF JOIN — "Join a Table to Itself"

A table joined against **itself**, treated as if it were two separate tables. Sounds strange until you see the use case: **finding an employee's manager, when the manager is also just... an employee.**

Suppose `employee` had a `manager_id` column (a foreign key pointing back to another `emp_id` in the *same* table):

```sql
SELECT
    emp.first_name  AS employee_name,
    mgr.first_name  AS manager_name
FROM employee emp
JOIN employee mgr ON emp.manager_id = mgr.emp_id;
```

**What's happening:** the exact same `employee` table is being used twice, under two different aliases (`emp` and `mgr`) — SQL treats them as if they were two completely separate tables, purely because we gave them different nicknames.

> 😄 It's the SQL equivalent of a person video-calling themselves from two different phones just to have a conversation. Weird to picture, extremely useful in practice — org charts, employee-reports-to-employee structures, category-has-a-parent-category trees, all lean on this exact pattern.

---

## 7. CROSS JOIN — "Every Combination of Everything"

No matching condition at all — every row from table A is paired with **every** row from table B.

```sql
SELECT e.first_name, d.dept_name
FROM employee e
CROSS JOIN department d;
```

With 100 employees and 25 departments, this returns **100 × 25 = 2,500 rows** — every possible employee-department pairing, whether it makes sense or not.

> ⚠️ This is almost never what you actually want by accident — if you forget the `ON` condition in a regular `JOIN`, MySQL silently treats it like a `CROSS JOIN` and floods you with a huge, mostly meaningless result. Genuine use cases exist (like generating every possible size/color combination for a product catalog), but "I forgot the `ON` clause" is the far more common reason people encounter one.

---

## 8. Table Aliasing — Do This Every Time

```sql
-- Without aliases — technically works, but painful to type and read
SELECT employee.first_name, department.dept_name
FROM employee
JOIN department ON employee.dept_id = department.dept_id;

-- With aliases — same result, much cleaner
SELECT e.first_name, d.dept_name
FROM employee e
JOIN department d ON e.dept_id = d.dept_id;
```

> The alias doesn't need to be a single letter — `emp`/`dept` works too — but keep it short. You'll be typing it constantly, and nobody wants to type `employee.first_name` fifteen times in one query.

## 9. All Five JOINs, Side by Side

| JOIN type | Returns |
|---|---|
| `INNER JOIN` | Only rows that match in **both** tables |
| `LEFT JOIN` | All rows from the **left** table, matched or not |
| `RIGHT JOIN` | All rows from the **right** table, matched or not |
| `FULL OUTER JOIN` | All rows from **both** tables (via `UNION` workaround in MySQL) |
| `SELF JOIN` | A table joined to **itself**, for relationships within one table |
| `CROSS JOIN` | **Every combination** of rows from both tables (no matching condition) |

## 10. Putting It All Together — A Realistic Query

```sql
-- List every employee with their department name and location,
-- showing "Unassigned" for anyone without a valid department
SELECT
    e.first_name,
    e.designation,
    COALESCE(d.dept_name, 'Unassigned') AS department,
    COALESCE(d.location, 'N/A') AS location
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id
ORDER BY department, e.first_name;
```
> `COALESCE()` is a small bonus function worth knowing — it returns the first non-`NULL` value from a list. Here, it swaps out any `NULL` department (from unmatched `LEFT JOIN` rows) with a friendlier `'Unassigned'` label instead of a blank cell.

## 11. Common Mistakes

**Mistake 1 — Forgetting the `ON` clause**
```sql
-- Accidental CROSS JOIN — 2,500 rows of chaos
SELECT e.first_name, d.dept_name FROM employee e JOIN department d;
```
Always double-check every `JOIN` has a matching `ON` condition unless a `CROSS JOIN` is genuinely what you meant.

**Mistake 2 — Ambiguous column names**
```sql
-- ❌ ERROR — both tables might have a column with this name
SELECT dept_id FROM employee JOIN department ON employee.dept_id = department.dept_id;
```
Once two tables are joined, always prefix shared column names with the table alias (`e.dept_id` or `d.dept_id`), even if it feels repetitive.

**Mistake 3 — Assuming LEFT JOIN and INNER JOIN always give the same row count**
They only match when **every** row on the left has a matching row on the right. The moment even one row doesn't match, `LEFT JOIN` returns *more* rows than `INNER JOIN` would, padded out with `NULL`s.

---

## 12. Quick Recap

| Keyword | What it does |
|---|---|
| `INNER JOIN` | Matches only — rows with no match on either side are dropped |
| `LEFT JOIN` | Keeps every row from the left table, `NULL`-fills unmatched right side |
| `RIGHT JOIN` | Keeps every row from the right table, `NULL`-fills unmatched left side |
| `FULL OUTER JOIN` | Keeps everything from both sides (needs `UNION` in MySQL) |
| `SELF JOIN` | Joins a table to itself, using two different aliases |
| `CROSS JOIN` | Every possible pairing, no matching condition at all |
| `COALESCE()` | Replaces a `NULL` with a fallback value — handy after a `LEFT`/`RIGHT JOIN` |
| Golden rule | Always alias your tables once more than one is involved, and always double-check your `ON` clause |
